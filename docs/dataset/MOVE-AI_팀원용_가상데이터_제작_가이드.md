# MOVE-AI 가상 데이터 제작 팀 가이드

> 목적: MOVE-AI MVP 개발 및 RAG 성능 테스트를 위한 가상 물류 현장 데이터를 팀원 4명이 동일한 기준으로 제작하기 위한 작업 가이드  
> 기준 스키마: `MOVE-AI_가상데이터_생성용_데이터셋_구조.md`  
> 제작 인원: 총 4명  
> 목표: 최종 승인 예상 원자 지식 약 140~160개

---

# 1. 우리가 왜 가상 데이터를 만드는가

이번 가상 데이터는 단순히 DB를 채우기 위한 더미 데이터가 아니다.

MOVE-AI에서 실제로 구현하려는 다음 흐름을 테스트하기 위한 데이터다.

```text
배송기사 음성 제보
        ↓
       STT
        ↓
AI가 현장 지식을 원자 단위로 구조화
        ↓
관리자가 원문과 비교하여 검수
        ↓
승인된 지식 저장
        ↓
RAG 검색
        ↓
Last 100m 배송 안내
```

따라서 데이터 제작 시 가장 중요한 것은:

```text
“문장 150개를 채우는 것”
```

이 아니라,

```text
“실제 기사님이 말할 법한 다양한 현장 경험을 만들고,
그 경험이 우리 구조에서 손실 없이 저장·검색되는지 테스트하는 것”
```

이다.

---

# 2. 최종 목표량

4명이 각각 하나의 가상 장소를 맡아 데이터를 제작한다.

## 1인당 권장 분량

```text
PLACE                  1개
PLACE_NODE             10~15개
ROUTE                  1~2개
ROUTE_SEGMENT          4~7개
FIELD_REPORT           약 10개
EXPECTED_KNOWLEDGE     약 35~40개
RAG_TEST_QUERY         5개
실제 음성 녹음 후보     5개
```

## 전체 예상 분량

```text
가상 장소                 약 4개
기사 제보                 약 40개
원자 지식                 약 140~160개
RAG 테스트 질문           약 20개
실제 음성 녹음 후보       약 20개
```

정확히 150개를 맞추는 것이 목적은 아니다.

최종적으로 약 140~160개의 다양한 지식이 확보되면 충분하다.

---

# 3. 왜 사람당 지식 40개를 직접 만들지 않는가

우리 서비스의 실제 입력은 `knowledge_item`이 아니라 기사님의 자유로운 음성 제보다.

따라서 다음처럼 만드는 것이 좋다.

```text
기사 제보 1건

“여기는 큰 탑차로 오면 정문이 좀 좁아요.
후문으로 들어가서 101동 뒤에 잠깐 세워놓고
오른쪽 출입구로 걸어가면 됩니다.”
```

이 한 제보에서:

```text
1. 정문은 대형 탑차 진입이 어렵다.
2. 후문으로 차량 진입이 가능하다.
3. 101동 뒤편에 임시 정차할 수 있다.
4. 정차 지점에서 오른쪽 출입구까지 도보 이동한다.
```

처럼 여러 개의 원자 지식이 나올 수 있다.

따라서 각자:

```text
기사 제보 약 10개
× 제보당 평균 3~4개 지식
```

을 만드는 방식으로 진행한다.

---

# 4. 팀원별 담당 장소

서로 비슷한 데이터만 생성되는 것을 막기 위해 장소 유형을 나눈다.

## 담당 A — 대규모 아파트 단지

중점 요소:

```text
정문 / 후문
차량 진입
지하주차장
차량 높이 제한
톤수 제한
임시 정차
동별 출입구
차량 → 도보 전환
엘리베이터
시간대 혼잡
```

예:

```text
“1.5톤 이상 탑차는 정문 쪽이 좀 좁아요.”
“101동 뒤에 잠깐 세워놓고 오른쪽 출입구로 들어가면 돼요.”
```

---

## 담당 B — 오피스·상업 빌딩

중점 요소:

```text
지하주차장
하역장
보안 게이트
정문 / 후문
화물 엘리베이터
일반 엘리베이터
대형 물품 반입
층별 이동
점심시간 혼잡
```

예:

```text
“큰 박스는 정문 로비로 못 들어가서 B2 하역장으로 가야 돼요.”
```

---

## 담당 C — 물류센터·산업시설

중점 요소:

```text
차량 크기별 출입 게이트
하역장
대기 지점
상·하차 위치
차량 높이
톤수
시간대 입차 제한
차량 이동 동선
```

예:

```text
“5톤 넘으면 1번 게이트 말고 2번 게이트로 들어가야 합니다.”
```

---

## 담당 D — 대형 복합시설

예:

```text
병원
대학교
대형 복합건물
여러 동이 연결된 시설
```

중점 요소:

```text
건물별 출입구
차량 정차 후 도보 전환
연결통로
내부 보행
엘리베이터
계단
목적 건물 구분
다단계 이동
```

예:

```text
“본관 앞에는 오래 못 세워서 뒤쪽 하역 지점에 차 두고
연결통로로 동관까지 걸어가야 돼요.”
```

# 5. 중요한 원칙 — 우리가 모든 현장 정보 유형을 예상할 수는 없다

실제 기사님들은 우리가 예상하지 못한 정보를 말할 수 있다.

예:

```text
“카트 끌고 방화문 지나갈 때 문턱이 높아요.”

“자동문 센서가 카트를 잘 못 잡아서 문이 빨리 닫혀요.”

“연결다리 바닥이 울퉁불퉁해서 유리 제품은 조심해야 돼요.”

“엘리베이터 앞보다 계단 뒤에 카트 잠깐 세워두는 게 편해요.”
```

이런 데이터를 기존 Category에 억지로 집어넣으면 안 된다.

우리 데이터 구조에서는 이런 경우:

```text
category = OTHER
custom_category_label = 자유 설명
```

을 사용한다.

예:

```text
category = OTHER
custom_category_label = "카트 이동 장애물"
```

`OTHER`는 잘못된 데이터가 아니다.

오히려 이번 테스트에서 반드시 필요한 데이터다.

---

# 6. 전체 데이터 중 예상 밖 정보를 일부러 포함한다

각자 만드는 지식 중 약 15~20%는 기존 분류에 딱 맞지 않는 정보로 만든다.

예:

```text
카트와 자동문 센서 문제
문턱으로 인한 적재물 낙하 위험
방화문 통과 어려움
연결다리 바닥 상태
특이한 경사로
카트 보관 위치
임시 대기 공간
특이한 회전문
화물 엘리베이터 버튼 위치
```

목표는:

```text
우리 데이터 구조가 모르는 정보가 들어왔을 때 깨지는지
```

확인하는 것이다.

---

# 7. 우리가 미리 등록하지 않은 위치도 일부 포함한다

기사님이 말하는 위치가 항상 기존 Node에 존재한다고 가정하면 안 된다.

예:

```text
“101동 들어가기 직전에 왼쪽으로 꺾는 좁은 길이 있는데
거기는 탑차가 돌기 힘들어요.”
```

그런데 데이터에 해당 Node/Segment가 없다면:

```text
target_type = UNKNOWN
target_resolution_status = UNRESOLVED
target_free_text = "101동 진입 직전 왼쪽으로 꺾는 좁은 길"
```

처럼 남긴다.

절대로 가장 비슷한 Node에 억지로 연결하지 않는다.

각 담당자는 최소 2~3개의 `UNRESOLVED` 위치 사례를 넣는다.

---

# 8. 기사 제보는 실제 말투처럼 만든다

가상 데이터를 LLM에게 생성시킬 때 가장 자주 생기는 문제는 문장이 너무 정형화되는 것이다.

## 피해야 하는 문장

```text
1.5톤 이상의 차량은 정문 진입이 제한되며 후문 이용이 권장됩니다.
```

너무 DB 문장 또는 안내문 같다.

## 원하는 문장

```text
여기 1.5톤 탑차로 오면 정문 쪽이 좀 빡빡해요.
저는 그냥 후문으로 들어가요.
```

또는:

```text
아 여기 점심때 오면 엘리베이터 진짜 오래 기다려요.
급하면 오른쪽 계단 쪽 확인하는 게 나아요.
```

말투가 모든 문장에서 똑같지 않도록 한다.

---

# 9. 한 제보에 여러 사실을 넣는다

한 문장에 정보 하나만 있는 데이터만 만들면 실제 음성 구조화 테스트가 너무 쉬워진다.

권장:

```text
한 제보당 2~5개 사실
평균 3~4개
```

예:

```text
“1.5톤 탑차는 정문이 좀 좁고요,
후문으로 들어가서 101동 뒤에 잠깐 세우면 돼요.
거기서 오른쪽 출입구까지는 걸어가야 하고
아침에는 후문 쪽이 좀 막혀요.”
```

이 경우 최소 4개의 원자 지식으로 나뉘어야 한다.

---

# 10. 하나의 지식에는 하나의 사실만 넣는다

잘못된 예:

```text
“정문은 좁고 후문으로 들어가서 101동 뒤에 세운 뒤
오른쪽 출입구로 걸어간다.”
```

이 전체를 하나의 Knowledge Item으로 만들면 안 된다.

분리:

```text
K1
정문은 대형 차량 진입이 어렵다.

K2
후문은 차량 진입이 가능하다.

K3
101동 뒤편을 정차 위치로 사용할 수 있다.

K4
101동 뒤편에서 오른쪽 출입구까지 도보로 이동한다.
```

---

# 11. 차량 정보와 도보 정보를 반드시 분리한다

예:

```text
“후문으로 차 들어가서 뒤에 세우고 오른쪽 문까지 걸어가면 돼요.”
```

최소:

```text
VEHICLE
후문 → 정차 지점

PEDESTRIAN
정차 지점 → 오른쪽 출입구
```

로 분리한다.

한 Knowledge Item에서:

```text
movement_mode = VEHICLE + PEDESTRIAN
```

같은 형태는 금지한다.

---

# 12. 조건 정보는 정확하게 만든다

다음 조건은 구조화해서 사용할 수 있다.

```text
차량 종류
최소/최대 톤수
차량 높이
차량 폭
요일
시간 범위
```

예:

```text
“1.5톤 이상이면 정문 들어가기 빡빡해요.”
```

↓

```text
min_tonnage = 1.5
```

중요:

```text
원문 = 1.5톤
구조화 = 2톤
```

처럼 숫자가 달라지면 안 된다.

---

# 13. 조건이 없는 정보에 조건을 만들어내지 않는다

원문:

```text
“정문은 큰 차가 들어가기 힘들어요.”
```

LLM이 임의로:

```text
min_tonnage = 2.5
```

처럼 숫자를 만들어내면 안 된다.

이 경우:

```text
vehicle_class = TRUCK
min_tonnage = null
```

같이 근거가 있는 수준까지만 저장한다.

---

# 14. “힘들다”와 “금지”를 구별한다

다음 표현:

```text
좁다
힘들다
불편하다
빡빡하다
```

는 일반적으로:

```text
CONDITIONAL
```

이다.

다음처럼 명확하게 금지된 경우:

```text
차량 출입 금지
들어갈 수 없다
통행이 막혀 있다
```

에만:

```text
PROHIBITED
```

를 사용한다.

---

# 15. 원문에 없는 대체 경로를 만들지 않는다

원문:

```text
“정문은 큰 차가 들어가기 힘들어요.”
```

여기서 알 수 있는 것은:

```text
정문에 제약이 있다.
```

뿐이다.

따라서:

```text
statement = "대형 차량은 정문 진입이 어렵다."
usage_scope = WARNING_ONLY
action_text = null
```

이어야 한다.

원문에 없는:

```text
“후문으로 들어가세요.”
```

를 추가하면 안 된다.

---

# 16. source_excerpt는 반드시 실제 제보에 있어야 한다

Transcript:

```text
“여기 1.5톤 탑차로 오면 정문이 좀 빡빡해요.”
```

가능:

```text
source_excerpt =
“1.5톤 탑차로 오면 정문이 좀 빡빡해요.”
```

불가능:

```text
source_excerpt =
“1.5톤 이상의 차량은 정문 진입 제한”
```

정리된 문장은 `statement`에 들어간다.

---

# 17. Route는 기사 제보와 별도로 먼저 만든다

우리 MVP에서 Route는 AI가 즉석에서 생성하는 것이 아니다.

```text
관리자가 미리 등록한 고정 경로
```

이다.

따라서 작업 순서도:

```text
PLACE
↓
NODE
↓
ROUTE
↓
ROUTE_SEGMENT
↓
기사 제보
↓
Knowledge
```

순으로 만드는 것을 권장한다.

기사 제보 때문에 Route를 계속 임의로 변경하지 않는다.

---

# 18. 일부러 헷갈리는 데이터를 만든다

RAG 성능 테스트를 위해 각자 최소 3개 이상의 어려운 사례를 만든다.

## 사례 1 — 동일 위치, 차량/도보 결과가 다름

```text
정문 차량 진입 금지
정문 보행자 출입 가능
```

## 사례 2 — 차량 크기에 따라 결과가 다름

```text
1톤 차량 가능
1.5톤 이상 조건부
```

## 사례 3 — 시간대에 따라 달라짐

```text
평소 통행 가능
08:00~09:00 혼잡
```

## 사례 4 — 비슷한 위치 이름

```text
101동 왼쪽 출입구
101동 오른쪽 출입구
```

## 사례 5 — 경고만 있고 대안 없음

```text
정문 대형 차량 진입 어려움
대체 출입구 정보 없음
```

## 사례 6 — Category가 OTHER인 정보가 정답

```text
“여기 카트 끌고 갈 때 자동문 조심해야 돼요.”
```

# 19. LLM 사용 순서

한 번에 40개 데이터를 전부 만들라고 요청하는 것보다 단계적으로 생성하는 것을 권장한다.

## Step 1 — 장소 설정

LLM에게 담당 장소의 구조를 먼저 설계하게 한다.

확인:

```text
장소가 지나치게 복잡하지 않은가?
Node 이름이 서로 구분되는가?
배송 시나리오를 만들 만한 구조인가?
```

---

## Step 2 — Node 생성

10~15개 정도 생성한다.

사람이 직접 확인한다.

특히:

```text
실외 → 실내 이동이 가능한가?
건물/출입구/정차지 관계가 자연스러운가?
```

를 확인한다.

---

## Step 3 — Route / Segment 생성

1~2개의 고정 Route를 만든다.

예:

```text
후문
→ 101동 뒤 정차지
→ 오른쪽 출입구
→ B 엘리베이터
→ 배송지
```

사람이 직접 순서를 확인한다.

---

## Step 4 — 기사 제보 생성

약 10건.

한 번에 10개를 생성해도 되지만 결과가 너무 비슷하면:

```text
5개 생성
→ 사람이 검토
→ 다른 유형 5개 추가
```

방식을 권장한다.

---

## Step 5 — Expected Knowledge 생성

각 제보에서 원자 지식을 추출한다.

목표:

```text
총 35~40개 정도
```

---

## Step 6 — 예상 밖 사례 추가

기존 데이터가 너무 정형적이면 별도로:

```text
OTHER
UNRESOLVED
custom label
```

사례를 추가한다.

---

## Step 7 — RAG 테스트 질문 생성

담당자별 5개.

이 중 최소 2개는 헷갈리는 질문으로 만든다.

# 20. LLM 생성 후 반드시 사람이 검수할 것

LLM 결과를 그대로 제출하지 않는다.

다음을 직접 확인한다.

## 참조 관계

```text
존재하지 않는 Node를 참조하지 않는가?
존재하지 않는 Segment를 참조하지 않는가?
Route Segment가 순서대로 연결되는가?
```

## 원문 충실성

```text
source_excerpt가 transcript에 실제 존재하는가?
원문에 없는 행동을 만들지 않았는가?
원문에 없는 숫자를 만들지 않았는가?
```

## 구조화

```text
차량/도보가 섞이지 않았는가?
한 지식에 여러 사실을 넣지 않았는가?
OTHER를 억지로 기존 Category로 변경하지 않았는가?
```

## 조건

```text
톤수/높이/시간이 원문과 일치하는가?
CONDITIONAL / PROHIBITED가 적절한가?
```

# 21. LLM에게 만들어 달라고 하면 안 되는 데이터

다음은 생성하지 않는다.

```text
실제 embedding vector
DB auto increment PK
비밀번호
실제 개인정보
공동현관 실제 비밀번호
실제 보안 코드
실제 사람의 전화번호
실제 내부 보안 정보
```

가상 장소의 현장 정보가 실제 장소의 사실인 것처럼 작성되지 않도록 한다.

# 22. 실제 장소명을 사용할 경우

가능하면 완전히 가상의 장소명을 사용하는 것을 권장한다.

예:

```text
해든마루 아파트
센트럴비즈 타워
동남 물류센터
미래복합의료센터
```

실제 장소를 배경으로 사용하는 경우에도:

```text
현장 제약
출입 방식
주차 정보
보안 정보
```

등은 실제 사실이라고 주장하지 않는다.

이번 데이터는 `SYNTHETIC` 데이터다.

# 23. 실제 음성 테스트용 문장 선택

각 담당자는 기사 제보 약 10개 중 5개를:

```text
audio_recording_candidate = true
```

로 지정한다.

단순한 문장만 고르지 않는다.

추천 조합:

```text
1개 — 짧고 단순한 제보
1개 — 여러 사실이 들어간 제보
1개 — 숫자/톤수/시간이 있는 제보
1개 — 차량 + 도보 정보가 함께 있는 제보
1개 — OTHER 또는 미등록 위치가 포함된 제보
```

총 4명이면 약 20개 음성 샘플을 확보할 수 있다.

# 24. 실제 녹음할 때는 문장을 그대로 읽지 않아도 된다

오히려 실제 말하듯 조금 변형하는 것이 좋다.

원본 가상 transcript:

```text
“1.5톤 탑차는 정문 진입이 어렵고 후문으로 들어갈 수 있습니다.”
```

실제 녹음:

```text
“어... 여기 1.5톤 탑차로 오면 정문이 좀 좁거든요.
저는 보통 후문 쪽으로 들어가요.”
```

테스트하고 싶은 요소:

```text
말 더듬음
“어”, “음” 같은 추임새
문장 순서 변화
구어체
숫자
비슷한 장소명
한 음성에 여러 사실
```

# 29. 팀 공통 기준

가장 중요한 것은 아래 세 가지다.

## 1. 원문을 잃지 않는다

분류가 애매해도 기사님이 전달한 의미 자체는 남아야 한다.

```text
transcript
statement
source_excerpt
```

가 핵심이다.

## 2. 모르면 억지로 분류하지 않는다

```text
OTHER + custom label
```

을 사용한다.

위치를 모르면:

```text
UNRESOLVED + target_free_text
```

를 사용한다.

## 3. AI에게 새로운 사실을 만들어내게 하지 않는다

AI는 기사 제보를:

```text
정리
분리
구조화
```

할 수 있지만,

```text
새로운 현장 사실
새로운 대체 경로
새로운 숫자 조건
```

을 만들어서는 안 된다.

# 30. 데이터 생성용 LLM 기본 요청문

실제 필드 구조는 반드시 함께 제공하는:

```text
MOVE-AI_가상데이터_생성용_데이터셋_구조.md
```

를 기준으로 한다.

LLM에는 다음 형태로 요청한다.

```text
너는 MOVE-AI 해커톤의 가상 물류 현장 데이터 제작 담당자다.

첨부한 `MOVE-AI_가상데이터_생성용_데이터셋_구조.md`를
이번 작업의 유일한 데이터 스키마 기준으로 사용해라.

내 담당 Prefix는 {A/B/C/D}다.

내 담당 장소 유형은:
{장소 유형}

이번 작업에서는 다음 데이터를 제작해라.

- PLACE 1개
- PLACE_NODE 10~15개
- ROUTE 1~2개
- ROUTE_SEGMENT 4~7개
- FIELD_REPORT 약 10개
- EXPECTED_KNOWLEDGE_ITEM 총 35~40개
- RAG_TEST_QUERY 5개
- audio_recording_candidate 5개

중요 규칙:

1. 기사 제보는 실제 배송기사가 말할 법한 한국어 구어체로 작성한다.
2. 한 제보에는 평균 3~4개의 사실을 포함한다.
3. 하나의 Knowledge Item에는 하나의 원자 사실만 넣는다.
4. VEHICLE과 PEDESTRIAN 사실을 하나의 Knowledge Item에 섞지 않는다.
5. 원문에 없는 숫자, 조건, 행동, 대체 경로를 생성하지 않는다.
6. source_excerpt는 transcript에 실제 존재하는 구절만 사용한다.
7. 모든 현장 정보를 기존 Category에 억지로 넣지 않는다.
8. 예상 밖 정보는 OTHER + custom label을 사용한다.
9. 기존 Node/Segment로 해결되지 않는 위치는
   UNKNOWN + UNRESOLVED + target_free_text로 보존한다.
10. 전체 지식의 약 15~20%는 예상 밖 정보가 되도록 한다.
11. 최소 2~3개의 UNRESOLVED 위치 사례를 포함한다.
12. 최소 3개의 헷갈리는 RAG 사례를 포함한다.
13. 실제 개인정보와 실제 보안정보를 생성하지 않는다.
14. 첨부 스키마에 없는 enum을 임의로 추가하지 않는다.
15. 임베딩 벡터, DB PK, 운영 로그는 생성하지 않는다.

먼저 장소 → Node → Route → Segment를 설계한 뒤
기사 제보와 Expected Knowledge를 생성해라.

생성 완료 후 스스로 참조 관계, source_excerpt, 숫자 조건,
원자성, 이동 방식 분리 여부를 검증하고 최종 결과만 출력해라.
```

# 31. 핵심 한 줄

이번 가상 데이터 제작의 목표는:

```text
우리가 생각한 현장 정보만 예쁘게 만드는 것
```

이 아니라,

```text

실제로 테스트할 수 있는 데이터를 만드는 것
```

이다.
