# MOVE-AI 기능 구현 원리 및 본선 PPT 준비 안내

> 대상: 기획자 / 디자이너 / 발표자료 제작 담당자  
> 목적: MOVE-AI가 실제로 어떤 원리로 동작하는지 이해하고, 본선 PPT와 데모 화면을 설계할 때 필요한 공통 이해를 맞추기 위한 자료  
> 주의: 이 문서는 개발 상세 명세가 아니라 **서비스 스토리, AI의 역할, 화면에서 보여줘야 할 핵심, 발표 논리**를 설명하는 문서다.

---

# 1. MOVE-AI를 한 문장으로 설명하면

**베테랑 배송기사의 현장 경험을 음성으로 수집하고, AI가 이를 검수 가능한 현장 지식으로 구조화한 뒤, 다음 배송기사의 Last 100m 배송 과정에서 필요한 정보만 다시 꺼내 보여주는 서비스**

핵심 흐름은 다음과 같다.

```text
베테랑 기사 현장 경험
        ↓
      음성 제보
        ↓
        STT
        ↓
 AI가 원자 단위 지식으로 구조화
        ↓
     관리자 검수
        ↓
 승인된 현장 지식 DB
        ↓
       RAG 검색
        ↓
현재 배송 상황에 맞는 정보 제공
        ↓
 Last 100m 배송 안내
```

MOVE-AI의 핵심은 단순한 길찾기가 아니다.

**주소와 지도만으로는 알 수 없는 현장 암묵지를 다음 기사에게 전달하는 것**이 핵심이다.

예:

- 어느 출입구로 들어가야 하는지
- 차량 높이 제한이 있는지
- 어디에 잠깐 정차할 수 있는지
- 카트를 끌고 갈 때 문턱이 있는지
- 특정 시간대에 엘리베이터가 혼잡한지
- 지도에는 없는 좁은 통로나 특이사항이 있는지

---

# 2. 우리가 해결하려는 문제

일반 지도나 내비게이션은 보통 건물 또는 주소까지 안내한다.

하지만 실제 배송의 마지막 구간에서는 이런 문제가 생긴다.

```text
주소에는 도착했는데 어디로 들어가야 하지?

정문으로 탑차가 들어갈 수 있나?

하역장은 어디지?

차는 어디에 세워야 하지?

이 건물은 화물 엘리베이터가 어디 있지?

카트로 지나가기 힘든 구간이 있나?
```

이 정보는 현장 경험이 많은 기사에게는 익숙하지만,
신규 기사나 처음 방문하는 기사에게는 존재하지 않는 정보에 가깝다.

즉 문제는:

```text
현장 경험은 존재하지만
개인의 기억에만 남아 있고
다음 기사에게 구조적으로 전달되지 않는다.
```

MOVE-AI는 이 경험을 데이터로 축적한다.

---

# 3. 서비스의 가장 중요한 차별점

MOVE-AI에서 AI는 "길을 마음대로 만들어주는 AI"가 아니다.

역할을 두 개로 나누어 이해해야 한다.

## 고정 Route

관리자가 미리 등록한 실제 Last 100m 배송 경로다.

예:

```text
후문
→ 지하 정차지
→ 건물 출입문
→ 내부 카트 통로
→ 화물 엘리베이터
→ 배송 인계점
```

Route의 순서는 AI가 즉석에서 바꾸지 않는다.

## 현장 Knowledge

Route를 이동하면서 알아야 할 현장 경험이다.

예:

```text
후문
- 2.3m 이상 차량은 진입 주의
- 오전 8시 30분에는 차량이 몰림

건물 출입문
- 카트 바퀴가 문턱에 걸릴 수 있음

화물 엘리베이터
- 점심시간에는 대기시간이 길어짐
```

따라서 서비스 구조는:

```text
고정된 배송 경로
+
상황에 맞는 현장 지식
=
MOVE-AI Last 100m 안내
```

이다.

# 4. 기능 1 — 기사 현장 팁 등록

베테랑 기사가 현장에서 직접 경험한 내용을 음성으로 남긴다.

예:

```text
"여기 큰 탑차로 오면 정문 쪽이 좀 빡빡해요.
저는 후문으로 들어가서 지하에 세워놓고,
오른쪽 출입구로 카트 끌고 들어가요.
점심때는 화물 엘리베이터가 많이 밀립니다."
```

사용자 화면에서는 어렵게 입력하지 않는다.

```text
장소 선택
↓
대표 위치 선택
↓
[녹음 시작]
↓
음성 녹음
↓
STT 결과 확인
↓
기사 본인이 텍스트 수정 가능
↓
[제보 제출]
```

핵심 UX:

**기사에게 직접 복잡한 카테고리나 데이터 필드를 입력하게 하지 않는다.**

기사는 평소 말하듯 경험을 말하면 된다.

---

# 5. STT 이후 AI가 하는 일

기사의 한 제보에는 여러 사실이 섞여 있다.

예:

```text
"정문은 큰 탑차가 좀 힘들고,
후문으로 들어가서 지하에 세우면 되고,
점심에는 엘리베이터가 많이 막혀요."
```

AI는 이를 한 문장으로 저장하지 않고,
여러 개의 원자 지식으로 분리한다.

```text
지식 1
정문은 대형 차량 진입이 어렵다.

지식 2
후문을 이용하여 진입할 수 있다.

지식 3
지하 정차 지점을 사용할 수 있다.

지식 4
점심시간에는 화물 엘리베이터가 혼잡하다.
```

이 과정에서 AI가 구조화하는 정보의 예:

- 어느 장소에 대한 정보인지
- 어느 Node 또는 Segment에 대한 정보인지
- 차량 이동 정보인지 / 도보·카트 이동 정보인지
- 접근 제한인지
- 경고인지
- 행동 안내인지
- 차량 톤수나 높이 조건이 있는지
- 특정 시간에만 적용되는지
- 실제 원문 중 어떤 구절을 근거로 판단했는지

---

# 6. AI가 마음대로 판단하지 않도록 하는 장치

이 기능에서 중요한 것은 AI가 그럴듯한 답을 만드는 것이 아니라,
**기사의 원래 경험을 왜곡하지 않고 구조화하는 것**이다.

예:

```text
기사 원문:
"1.5톤 차로 들어가면 좀 빡빡해요."
```

AI가 이렇게 만들면 안 된다.

```text
"1.5톤 이상 차량은 진입 금지"
```

"힘들다"와 "금지"는 다른 정보다.

또한 원문에 없는:

```text
"그러니 후문으로 진입하세요."
```

같은 대체 행동도 AI가 새로 만들어서는 안 된다.

---

# 7. 미리 등록하지 않은 정보도 버리지 않는다

실제 기사 제보는 우리가 예상하지 못한 위치를 포함할 수 있다.

예:

```text
"하역장 들어가기 직전에 왼쪽으로 꺾는 좁은 길이 있는데,
거긴 큰 차가 돌기 힘들어요."
```

그런데 시스템에 "왼쪽으로 꺾는 좁은 길"이라는 위치가 아직 등록되어 있지 않을 수 있다.

이때 MOVE-AI는:

```text
비슷한 기존 위치에 억지로 연결
```

하지 않는다.

대신:

```text
미등록 위치
UNRESOLVED
"하역장 진입 직전 왼쪽 좁은 길"
```

형태로 보존한다.

나중에 관리자가 확인한 뒤 새로운 Node 또는 Segment를 추가할 수 있다.

즉 장소 정보는 처음부터 완성되어 있는 것이 아니라,
**기사들의 제보를 통해 계속 고도화될 수 있다.**

# 8. 기능 2 — 관리자 검수

AI가 추출했다고 바로 서비스에 사용하지 않는다.

```text
기사 제보
↓
AI 구조화
↓
승인 전 Draft
↓
관리자 확인
↓
승인된 Knowledge
```

관리자는 다음을 비교한다.

```text
실제 음성
STT 원문
AI가 추출한 지식
```

예상 관리자 화면:

```text
[음성 재생]

기사 원문
"1.5톤 탑차로 오면 정문이 좀 빡빡해요."

AI 추출 결과

Target
정문

내용
1.5톤 탑차는 정문 진입이 어렵다.

적용 범위
차량

원문 근거
"1.5톤 탑차로 오면 정문이 좀 빡빡해요."

[승인] [수정 후 승인] [반려]
```

이 구조의 의미:

**AI 자동화 + 사람 검수**

신뢰할 수 있는 현장 지식을 만들기 위한 Human-in-the-loop 구조다.

---

# 9. 승인된 지식은 어떻게 검색되는가

승인된 Knowledge는 단순 문자열 검색만 하지 않는다.

문장의 의미를 벡터로 바꾸는 **Embedding**을 생성한다.

예:

```text
"오후 5시에는 카트 두 대가 마주 지나가기 어렵다."
```

↓

```text
Embedding Vector
[0.021, -0.18, 0.44, ...]
```

MVP에서는 이 벡터를 별도 Vector DB가 아니라
**MariaDB의 Knowledge 데이터와 함께 저장**한다.

이유:

- 현재 지식 규모가 약 140~160개 수준
- 별도 Vector DB를 추가할 필요가 없음
- 배포 구조를 단순하게 유지할 수 있음
- 해커톤 데모 안정성이 중요함

향후 데이터가 대규모로 늘어나면 Vector DB로 확장할 수 있다.

# 10. RAG는 단순한 "AI 검색"이 아니다

RAG 검색은 두 종류의 판단을 함께 사용한다.

## 1단계 — 구조화 조건

현재 상황에 맞지 않는 지식을 먼저 걸러낸다.

예:

```text
현재 장소
현재 차량 종류
차량 톤수
차량 높이
현재 시간
현재 Route / Segment
현재 이동 방식
```

예:

```text
현재 차량 = 5톤 트럭
```

이라면

```text
1톤 이하 차량용 정보
```

를 그대로 보여주면 안 된다.

## 2단계 — 의미 기반 검색

남은 후보 중에서 현재 상황과 의미적으로 가까운 지식을 Embedding 유사도로 찾는다.

결국:

```text
구조화된 조건 검색
+
Embedding 의미 검색
=
Hybrid RAG
```

를 사용한다.

# 11. 왜 Embedding만으로 검색하지 않는가

예를 들어 DB에 이런 두 지식이 있다고 하자.

```text
지식 A
1톤 차량은 이 출입구 이용 가능

지식 B
5톤 차량은 이 출입구 이용 어려움
```

사용자 상황:

```text
현재 차량 = 5톤
```

Embedding 관점에서는 두 문장 모두
"차량 + 출입구 + 이용"이라는 의미가 비슷하다.

따라서 단순 Vector 검색만 하면 둘 다 높은 점수로 나올 수 있다.

하지만 MOVE-AI에서는:

```text
차량 톤수
높이
시간
요일
위치
```

같은 데이터가 이미 구조화되어 있다.

따라서 이런 값은 코드로 정확하게 비교하고,
문장의 의미가 필요한 부분만 Vector 검색을 활용한다.

---

# 12. Last 100m에서는 무엇이 보이는가

기사에게는 데이터 구조를 보여주지 않는다.

예:

```text
3 / 5 단계

상온창고 카트 통로

다음 안내
통로 끝까지 이동하세요.

주의
오후 5시 전후에는 빈 팔레트가 많아
카트 두 대가 마주 지나가기 어렵습니다.

팁
반대편에서 카트가 오면
한 대를 먼저 보낸 뒤 이동하는 것이 편합니다.

[다음]
```

기사 입장에서는:

```text
지금 어디로 가야 하는지
+
지금 여기서 무엇을 조심해야 하는지
```

만 알면 된다.

# 13. 기능 3 — 고객 메시지 답장 보조

핵심 기능 완성 후 추가하는 보조 기능이다.

예:

```text
고객 메시지
"언제쯤 오세요?"
```

AI:

```text
의도 = 배송 ETA 문의
```

기사 화면:

```text
추천 답장

[어느 구역이신가요?]
```

또는 배송 순서 정보가 존재한다면:

```text
고객
"105동 언제 오세요?"

추천 답장
[오후 2시~4시 사이 도착 예정입니다.]
```

중요:

**AI가 자동으로 답장을 보내지 않는다.**

기사에게 후보를 제안하고,
기사가 직접 버튼을 눌러야 전송된다.

# 16. 우리가 만든 가상 데이터셋의 의미

현재 A / B / C / D 네 종류의 가상 장소 데이터셋을 만들고 있다.

장소 예:

```text
A — 대규모 아파트
B — 오피스/상업 빌딩
C — 물류센터/산업시설
D — 대형 복합시설
```

이 데이터는 단순히 화면을 채우는 Dummy Data가 아니다.

두 역할이 있다.

## 역할 1 — 서비스 Seed

```text
장소
Node
Route
Segment
Knowledge
```

를 실제 DB에 넣고 서비스를 테스트한다.

## 역할 2 — AI 정답 데이터 Gold

예:

```text
기사 원문
↓
AI가 실제로 구조화
↓
우리가 사람이 검수한 expected Knowledge와 비교
```

RAG도:

```text
테스트 질문
↓
실제 검색
↓
기대 Knowledge와 비교
```

할 수 있다.

즉 발표에서:

```text
"AI가 잘 작동합니다."
```

가 아니라,

```text
"사전에 사람이 검수한 Gold 데이터를 기준으로
구조화와 검색 결과를 검증합니다."
```

라고 설명할 수 있다.

# 17. 본선 데모에서 가장 중요한 장면

본선에서는 기능을 각각 따로 보여주기보다
**한 정보가 생성되어 다시 사용되는 과정**을 보여주는 것이 좋다.

## Scene 1 — 문제

처음 방문한 기사:

```text
"주소까지 왔는데 어디로 들어가야 하지?"
```

일반 지도:

```text
건물 위치까지만 안내
```

## Scene 2 — 베테랑의 경험

```text
"큰 탑차는 정문 쪽이 좀 빡빡하고,
후문으로 들어가면 편해요.
점심에는 화물 엘리베이터가 많이 막힙니다."
```

## Scene 3 — AI 지식화

화면에서 기사 발화가:

```text
정문 대형차 진입 주의

후문 이용 정보

점심시간 엘리베이터 혼잡
```

처럼 분리되는 장면.

## Scene 4 — 관리자 승인

```text
AI 결과를 사람이 확인
→ 승인
```

## Scene 5 — 다음 기사

다른 기사가 같은 장소에 배송을 시작.

## Scene 6 — Last 100m

```text
후문으로 이동하세요.

주의
대형 차량은 정문 진입이 어렵습니다.

주의
현재 시간대에는 화물 엘리베이터가 혼잡합니다.
```

## 핵심 메시지

```text
한 사람의 경험이
다음 사람의 길이 된다.
```

또는:

```text
사라지는 현장 경험을
다음 배송을 위한 데이터로.
```

# 18. PPT에서 기술을 설명할 때 피해야 하는 표현

너무 개발자 중심으로 표현하면 기획 메시지가 약해질 수 있다.

예:

```text
MariaDB JSON vector + NumPy cosine similarity
```

를 메인 슬라이드에 크게 넣을 필요는 없다.

대신:

```text
현장 지식의 의미를 Embedding으로 저장
→ 현재 상황과 의미적으로 가까운 경험 검색
```

이라고 설명하고,

기술 스택 슬라이드에서만 실제 구현을 보여주는 것이 좋다.

# 19. 본선 PPT 추천 흐름

## 1. 문제 제기

"지도는 건물까지 알려주지만, 배송은 건물 안에서 끝난다."

보여줄 내용:

- 주소 이후의 정보 공백
- 베테랑 기사만 아는 현장 팁
- 기사 교체 시 경험 소실

## 2. 기존 문제

```text
현장 경험
→ 기사 개인의 기억

→ 신규 기사 시행착오 반복
```

## 3. MOVE-AI Solution

한 장에서:

```text
말하면

→ 사람이 검수하고
→ 다음 기사에게 다시 안내
```

```text

→ STT

→ 검수
→ Knowledge DB
→ RAG
→ Last 100m
```

## 5. AI Knowledge Extraction

기사의 자연어가

```text

         ↓

└ 시간대 혼잡
```

## 6. 신뢰성 확보

```text
AI가 자동 확정하지 않음
→ 관리자 검수
→ 승인된 지식만 실제 안내에 사용
```

Human-in-the-loop 강조.

---

## 7. RAG / Embedding 원리

복잡하게 설명하지 않고:

```text
현재 기사 상황
+
승인된 현장 경험 DB
↓
조건이 맞는 정보 선별
↓
의미가 가까운 경험 검색
```

Hybrid RAG.

## 8. Last 100m

지도/경로 UI와 함께:

```text
고정 Route
+
현장 Warning
+
Action Tip
```

표시.

# 20. 디자이너에게 특히 전달해야 할 포인트

## 현장 지식은 "채팅 답변"처럼 보이면 안 됨

서비스의 핵심은 AI 채팅이 아니다.

기사에게는:

```text
Warning

```

형태의 짧은 카드가 적절하다.

예:

```text
⚠ 차량 높이 주의

```

```text
→ 이동 안내
하역 후 오른쪽 출입구로 이동하세요.
```

## AI Extraction 화면

기술적인 JSON을 그대로 보여주기보다는:

```text
기사 원문
```

처럼 카드 형태로 시각화.

# 21. 발표에서 AI를 설명하는 가장 쉬운 방법

다음 세 문장으로 충분하다.

### AI 1 — 이해

"기사가 자연스럽게 말한 현장 경험을 AI가 여러 개의 작은 지식으로 분해합니다."

### AI 2 — 저장

"사람이 검수한 정보만 승인하고, 의미 검색이 가능하도록 Embedding해 저장합니다."

### AI 3 — 활용

"다음 배송에서는 현재 차량, 시간, 위치와 관련 있는 경험만 RAG로 찾아 Last 100m 경로에 함께 보여줍니다."

# 22. 반드시 구분해서 설명할 것

## Route

```text
어디로 이동할 것인가
```

관리자가 미리 정의.

## Knowledge

```text
그곳에서 무엇을 알고 있어야 하는가
```

기사 경험에서 생성.

## RAG

```text
현재 상황에서 어떤 Knowledge가 필요한가
```

를 검색.

이 세 개를 섞지 않는 것이 중요하다.

# 23. 발표용 핵심 문장 후보

### 문제

"배송의 마지막 100m에는 지도에 없는 정보가 존재합니다."

### 해결

"기사의 경험을 말로 남기면, MOVE-AI가 다음 배송에서 사용할 수 있는 현장 지식으로 바꿉니다."

### 기술

"AI가 현장 경험을 구조화하고, 사람의 검수를 거친 뒤 Hybrid RAG로 현재 배송 상황에 맞는 정보만 검색합니다."

### 가치

"개인의 경험을 일회성 노하우가 아닌 조직의 배송 데이터로 전환합니다."

### 데모 메시지

"한 기사가 남긴 한마디가 다음 기사의 시행착오를 줄입니다."

# 24. 본선 PPT 제작 시 가장 중요한 한 장

시간이 부족하다면 아래 그림을 가장 잘 만들어야 한다.

```text
[베테랑 기사]
     │
   음성 팁
     ▼
[AI 지식화]
     │
 관리자 검수
     ▼
[현장 Knowledge DB]
     │
 RAG 검색
     ▼
[다음 배송기사]
     │
고정 Last 100m Route
+
현재 상황에 맞는 현장 팁
```

이 그림 하나가 MOVE-AI 전체 구조를 설명할 수 있어야 한다.

# 25. 최종 요약

MOVE-AI의 핵심은 세 단계다.

```text
1. 경험을 수집한다.
기사 음성 → STT

2. 경험을 신뢰 가능한 데이터로 만든다.
AI 구조화 → 관리자 검수 → Knowledge + Embedding

3. 경험을 다시 사용한다.
Hybrid RAG → 고정 Last 100m Route에 현장 팁 제공
```

따라서 본선 발표에서도:

```text
AI 기능 자체
```

보다

```text
현장 경험이
수집되고
검증되고
다음 배송에서 다시 쓰이는 전체 순환 구조
```

를 보여주는 것이 가장 중요하다.

# 26. 기획자 / 디자이너가 기억할 핵심

- MOVE-AI는 챗봇 서비스가 아니다.
- MOVE-AI는 AI가 길을 마음대로 만드는 서비스도 아니다.
- Route는 미리 등록된 고정 배송 경로다.
- AI의 핵심 역할은 기사 자연어를 구조화된 현장 지식으로 바꾸는 것이다.
- AI 결과는 사람이 검수한다.
- 승인된 지식만 실제 안내에 사용한다.
- Embedding은 현장 경험의 의미 검색을 위해 사용한다.
- 차량/시간/위치 같은 명확한 조건은 구조화 데이터로 함께 판단한다.
- 최종적으로 기사에게 보여주는 것은 복잡한 데이터가 아니라 간단한 Warning / Action / Tip이다.
- 발표의 핵심은 "한 기사의 경험이 다음 기사에게 재사용된다"는 순환 구조다.
