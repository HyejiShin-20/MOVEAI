# 역할 분담과 하네스 운용

> 본선 당일 누가 무엇을 하는지. **팀 합의 후 확정한다.** 아래는 초안이다.

---

# 1. 하네스는 한 명만 운용한다

**여러 명이 동시에 하네스를 돌리지 않는다.**

이유:

- `IMPLEMENTATION_STATUS.md`가 하나다. 두 세션이 동시에 고치면 진행 상태가 깨진다.
- 같은 파일을 두 세션이 만지면 병합 충돌이 나고, 해커톤에서 이걸 푸는 시간이 이득보다 크다.
- 계약(API DTO)을 각자 바꾸면 프론트가 멈춘다.

하루짜리 일정에서 병렬 하네스는 **거의 항상 손해**다.

## 그럼 나머지 세 명은 노는가

아니다. 하네스가 못 하는 일이 많다.

---

# 2. 역할

## R1 — 하네스 운용  (1명)

유일하게 `backend/`, `ai-service/`를 건드린다.

```
Phase 단위로 지시 → 30~60분마다 결과 확인 → 어긋나면 교정
Phase 완료 시 커밋 확인 + IMPLEMENTATION_STATUS.md 갱신 확인
```

**주의** — 하네스에게 맡겨두고 다른 일을 하면 반드시 옆길로 샌다.
이 사람은 하네스 운용에만 집중한다.

## R2 — 프론트엔드  (1명)

`frontend/`만 건드린다. 백엔드 파일을 만지지 않는다.

```
Phase 1 이후    화면 뼈대를 Mock 데이터로 먼저 만든다
Phase 2b 이후   실제 API에 연결
```

**API 계약은 `05B`에 이미 확정돼 있다.** 백엔드가 안 끝나도 Mock으로 화면을 다 만들 수 있다.
계약이 마음에 안 들어도 임의로 바꾸지 말고 R1에게 말한다.

## R3 — 데이터 · 시연  (1명)

```
오전   임포트 검증, 시연용 음성 녹음, DB 상태 점검
오후   DEMO_SCRIPT §7-2 동작 점검 12항목 반복 확인
종료 후 시연 영상 촬영
```

**시연용 음성은 미리 여러 번 녹음해 둔다.** 당일 처음 녹음하면 STT가 못 알아듣는 경우가 생긴다.

## R4 — 발표 · 문서  (1명)

```
오전   PPT 뼈대 (기획디자인 이해자료 5부의 12장 구성 그대로)
오후   실제 화면 스크린샷을 PPT에 반영
종료 전 발표 대본, 예상 질문 답변 준비
```

**PPT는 개발과 무관하게 진행 가능하다.** 화면 스크린샷만 나중에 끼워 넣으면 된다.
`MOVE_AI_기획디자인_이해자료.pdf` 하나로 충분하다.

---

# 3. 합류 지점

```
T+1.5h  Phase 1 완료   → R2가 API 연결 준비 시작 (Mock으로)
T+4.0h  Phase 2b 완료  → R2가 실제 API 연결
T+8.0h  Phase 4 완료   → R3가 1막 동작 점검
T+11.5h Phase 7 완료   → R3가 2막 동작 점검, 이후 촬영
```

R1은 이 시각에 **다른 사람에게 알린다.** 안 알리면 R2가 계속 Mock으로 작업한다.

---

# 4. 인원이 부족하면

3명이면 **R3와 R4를 한 사람이** 맡는다. 둘 다 오후에 몰리므로 빡빡하지만 가능하다.

2명이면 **R1 + (R2·R3·R4)** 로 나눈다. 이 경우 프론트를 최소한으로 만들고
화면 완성도보다 **동작하는 흐름**을 우선한다.

---

# 5. 공통 규칙

```
backend/ · ai-service/  →  R1만 수정
frontend/               →  R2만 수정
docs/                   →  누구나. 단 IMPLEMENTATION_STATUS.md 는 R1만
datasets/               →  수정 금지 (검증 통과 상태)
```

**계약(05B)을 바꿔야 할 상황이 생기면 반드시 R1을 통한다.**
각자 고치면 그 순간 프론트와 백엔드가 갈라진다.
